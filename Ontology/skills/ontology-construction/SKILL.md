# 原生本体构建

本技能负责将设计落实为可维护的原生语义文件。先按[建模原则](../../references/modeling-principles.md)核对设计，再按[OWL 与 SHACL 模式](references/owl-shacl-patterns.md)实现类、属性、公理、实例及扩展。

对应[本体构建工作流](../ontology-builder/SKILL.md)的文档路线阶段 6–7（OWL 本体生成、本体集成），或知识库路线阶段 3（可重复构建）。已有本体需要概念对齐或冲突消解时，先按[变更与复用](../ontology-validation/references/change-and-reuse.md)完成融合决策，再执行这里的文件集成。设计缺口交由[业务本体设计](../business-ontology-design/SKILL.md)处理，不重复已经完成的阶段。

以下内容规定原生序列化、加载和构建证据；按[输出规范](../../CONTRACT.md)落实目录及格式。后端能力决定执行和验证方式，模型语义仍须符合业务依据与已确认设计。

## 输入、输出与边界

输入应包括能力问题、来源与确认、术语、对象身份、字段与关系契约、独立案例预期及缺口。输入缺少影响结论的口径时，继续构建确定部分并明确受限范围。

新项目直接维护 `subontologies/<domain>_ontology.owl`、`shapes.ttl`、`provenance.ttl`、`mapping.ttl` 和 `data/instances_<domain>.owl`。规则由[规则设计与实现](../ontology-inference-design/SKILL.md)维护 `rules/<domain>/<domain>_rules.swrl`；本阶段将源文件登记到 `integration/load-plan.ttl` 并构建集成入口。`.owl` 和 `.swrl` 固定 RDF/XML，`.ttl` 固定 Turtle；不生成 JSON，不把条件塞入字符串再交由另一个解释器执行。既有 `ontology.ttl` / `rules.swrl` / `inputs/facts.ttl` 扁平包仍兼容，不因更新方法库批量迁移业务项目。

## 1. 建立命名与版本

- 新项目选定稳定的绝对 IRI 命名空间；既有项目优先保留已有 IRI。显示名称与身份分开，为项目定义的类和属性提供中文 `rdfs:label`、清楚定义及来源；有跨语言需求时补充经核对的语言标签。复用外部术语时保留其 IRI 和定义，按需要提供本地说明。
- 新建术语默认采用 UpperCamelCase 类名、lowerCamelCase 属性名；复用既有合法 IRI 时保留身份并记录差异。这是项目命名约定，不构成正式标准符合性证明。
- 命名空间按实际管理与复用范围确定，`example.org` 只用于示例；示例域名、英文命名或 `has/is` 前缀不构成标准符合性依据。双语别名不能代替语义对齐，改标签不改身份。
- 按领域设计声明稳定域 ID、`owl:Ontology` IRI、版本和说明，并登记模块归属。用固定版本标识与文件指纹锁定发布；采用 `owl:versionIRI` 时保持其与版本一致，不把本体 IRI、术语命名空间、版本 IRI 和磁盘路径混为一项。
- 记录来源。概念含义发生实质变化时评估新 IRI 或迁移方案，不能只改标签掩盖不兼容变更。
- 自定义元数据词汇说明其含义和取值。例如人工状态、确认范围与运行状态没有一个自动适用于全部项目的 OWL 标准定义。

## 2. 构建类与公理

把明确的业务定义落为类与关系，并逐条检查公理实际表达什么：

| 表达 | 使用条件 | 常见误用 |
|---|---|---|
| `rdfs:subClassOf` | 每个子类成员都属于父类 | 用于包含、先后或字段分组 |
| `owl:equivalentClass` | 两边分类条件充分且必要 | 把一个必要条件误写成完整定义 |
| `owl:disjointWith` | 两类绝不共享同一实例 | 把不同时间的状态误写成永久互斥 |
| 限制类 | 业务定义需要表达量化或数量语义 | 当作表单必填或字段校验 |
| `owl:sameAs` | 已有证据确定同一对象 | 用于模糊匹配或临时关联 |

不要因为工具能够解析这些三元组就宣布推理支持。特别核对开放世界语义、对象同一性和后端支持的 OWL 范围；后端不支持时保留正确模型、选择兼容后端或记录执行缺口，不删减有业务依据的有效语义。继承环可能表达等价，并不一概是语法错误；但意外的环和不可满足类需要解释与检查。

“抽象类”若仅表示业务建模意图，应注明它的含义；OWL 没有一个通用的 `abstract` 开关来禁止直接实例化。确需输入限制时定义相应校验，不自行添加不存在的 OWL 机制。标准文本的章节结构、信息内容和图表呈现也不默认建立为业务类；按[文档建模范围](../business-ontology-design/references/document-to-model.md)决定是否为独立知识对象。

## 3. 定义属性、身份与单位

为对象属性明确两端业务类型、方向和关系语义；为数据属性明确 XSD 类型、单位、时间及来源。统一属性的 domain/range 必须符合所有使用场景；同一属性声明多个 domain 的语义通常是同时属于这些类，并不是“任选其一”。

只有充分证据支持时才声明函数性、逆函数性、传递性、对称性或逆属性。`owl:FunctionalProperty` 描述逻辑上的至多一个取值，不是自动抛出重复记录错误的数据库约束。

属性名或动词类别不能代替证据：`belongsTo` 不天然逆函数，`relatedTo` 不天然对称，`hasPart` 是否传递取决于所表达的部分关系。数据属性不使用对象属性专属的对称、传递或互逆特征；父类共享约束不能错误施加到语义不同的子类。

身份契约落到映射及校验，不仅写一个 `id` 字段。多个周期或快照的状态使用独立记录或事件表达，避免给永久对象同时断言语义上互斥的当前值。金额使用 `xsd:decimal`，不得借换类型自行补舍入或容差规则。

## 4. 生成 SHACL 输入约束

从数据契约推导约束，而不是把每个属性一律设为必填。分别说明原始输入、转换后输入与推导结果校验使用哪个图及哪些形状。

1. 用 `sh:targetClass` 或明确目标选择待校验节点，检查实际输入类型是否覆盖目标。
2. 按契约设置 `sh:path`、`sh:datatype`/`sh:class`、`sh:minCount`、`sh:maxCount`、`sh:in` 等。
3. 范围与边界只使用有来源的业务值。缺失字段若属于允许的未知输入，不能无条件用必填约束提前拒绝；由项目明确该阶段的策略。
4. 为复合身份、关联键、主体/周期一致性设置额外约束。需要 SHACL-SPARQL 时先验证实际后端支持和查询范围。
5. `sh:closed` 按需使用，并考虑类型和来源元数据，避免无意排斥合法字段；不以关闭形状代替身份验证。
6. 检查形状自身合法性和至少一组正常/违规数据。报告只包含零个目标节点时，不能据此宣称业务数据校验充分。

OWL domain/range 会参与类型推导，SHACL 检查图是否满足约束；二者目的不同。声明 range 不会自动使错误输入转换成合法值。校验前是否扩展 RDFS/OWL 类型必须由运行契约明确，不靠工具默认行为猜测。

## 5. 连接来源、映射和事实

- `provenance.ttl` 为模型、规则、确认和缺口提供可定位依据；未给出的版本与生效期如实未知。
- `mapping.ttl` 指向实际存在的类和属性，并记录身份、转换、空值、单位、时间、连接规则与实现状态。
- 默认将领域 ABox 放在 `data/instances_<domain>.owl`，与 TBox 和规则分开维护；实际运行可另选明确登记的输入快照。真实资料与合成案例明确标记，每条字段与关系值有来源证据。沿用扁平包时事实仍放 `inputs/`。
- 输入不预先写入待验证的分类、规则结论或人工审批结果。测试需要的已知类型或前提与目标结论要明确区分。
- 不擅自连接或修改外部系统。离线抽取、模拟输入和实际接口联调分别登记，不能把字段映射完成当作接口已接通。

## 6. 组织模块并接入规则

按[领域组织方法](../../references/domain-organization.md)落实业务域与文件归属。一个域的类、属性和公理默认共同放入它的领域本体；技术拆分如有必要须保持域归属，不能把 `classes`、`properties` 等文件名当成业务域。

1. 为 TBox、规则、ABox 登记领域、文件角色、格式、稳定 IRI、版本和依赖；所有路径按加载清单约定解析到包内本地文件。共享术语复用原 IRI；跨域桥接公理和规则有明确归属、来源与案例。
2. 默认由领域 TBox 与规则源构建 `integration/merged_ontology.owl`，作为可重新生成的派生模型入口。ABox 按本次运行显式加载，不默认写入集成模型；若提供冻结演示快照，单独标记并防止与运行输入重复加载。只改源文件后重建，不手工维护第二份政策。
3. 合并前检查 IRI 冲突、重定义、版本及规则引用；合并时保持各源文件空白节点独立、RDF 列表完整。图并集不自动实现概念对齐、同名实体合一或冲突消解。合并后核对来源覆盖并运行集成案例。
4. 可以声明纯 `owl:imports` 入口，但须实现离线 IRI 映射并验证完整依赖闭包，分别覆盖 TBox 和所需规则。仅有一个导入声明不能称为全量模型；不得自动联网解析依赖。
5. `integration/load-plan.ttl` 是加载契约，不是自动生效的运行器。明确实际后端如何读取清单或展开为调用参数，是否支持导入、规则及多个事实文件；提供真实构建与运行命令。

[Ontology-tools](../../Ontology-tools/README.md) 的 `local-rules-v1` 规则执行接口读取固定的扁平 `ontology.ttl`、`rules.swrl` 与 `inputs/facts.ttl`（或显式事实参数），不读取领域加载清单，也不支持 `owl:imports`。选择它时，须实现可重建的扁平兼容导出、保留源文件到导出文件的映射并验证语义；或者选用支持当前结构的其他后端。改变目录或文件后缀不构成适配，不为适配删除不支持的公理或规则。

规则阶段必须使用本体已声明的类和属性。检查规则变量、数据类型、单位、对象关联和快照范围；条件未落到规则或被后端忽略时，不得宣称已实现。SWRL 不承载文件写入、审批、外部请求等副作用。

## 7. 构建检查与交接

构建结果回到所选工作流：文档路线进入阶段 8–9，知识库路线进入阶段 4–5。按[推理设计](../ontology-inference-design/SKILL.md)核对规则，使用[执行方法](../ontology-execution/SKILL.md)记录运行证据，并按[质量验收](../ontology-validation/SKILL.md)完成检查。没有后端时保留模型及执行缺口，不编造运行命令或通过记录。

构建阶段最低检查：

- 文件存在、编码/格式正确；所有 RDF 列表和规则引用可解析。
- 模型、来源、映射、规则与事实的 IRI 一致，无拼写造成的孤立概念。
- domain/range、类公理、身份与时间粒度符合业务定义。
- 术语表与实际 IRI、中文标签、定义和来源一致；复用或扩展未悄然改写核心定义，标准符合性未超出核验范围。
- 每条决定性约束有来源，SHACL 的目标与实际输入一致。
- 域、模块、IRI 和版本登记一致；模块可离线解析，依赖固定，不依赖自动获取远程内容。
- 加载清单覆盖所需本体与规则；集成入口可从源重建，ABox 加载范围明确，没有用 imports 声明冒充完整闭包。
- 所选后端确实读取约定文件；兼容导出与源文件图语义一致，且实际语义支持已经核对。
- 映射设计、真实转换实现、推理执行和业务动作明确区分。
- 不支持的表达、缺少的数据和人工范围已经列明。

生成或修改模型后，使用 [OWL DL 检查入口](../../Ontology-tools/OWL-DL.md)或经验证的等效后端，检查完整 TBox 集合与选定 ABox 的全局一致性和具名类可满足性；SWRL 单独验证，失败或未执行范围明确记录。

交付依照单包规范写 README、运行期 SKILL、验收记录和指纹清单。格式检查、逻辑一致性、SHACL 和黄金案例分别报告；其中任何一项通过都不能代替其他项。
