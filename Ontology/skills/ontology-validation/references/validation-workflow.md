# 五层验证手册

本手册保留语法、语义、规则、推理、集成五层方法以及部署前、变更后和异常排查场景。通用验收字段与覆盖率口径以[验收清单](acceptance-checklist.md)为准；本手册细化实际执行，不另设通过阈值。

## 1. 语法与命名

- 识别实际格式：`.owl`/`.swrl` 新交付为 RDF/XML，`.ttl` 为 Turtle。RDFLib 的 `xml` 不是 OWL/XML；真正 OWL/XML 需要支持该语法的解析器/转换器。
- 所有读取限于明确本地输入。RDF/XML拒绝DTD、外部实体；导入须有本地映射，不能因IRI形似URL而联网。
- OWL解析检查类、属性、公理、列表和声明；SWRL检查 `swrl:Imp`、非空合法 body/head、RDF列表终止、原子种类、谓词声明、变量绑定及内建参数。仅查询到规则ID不能证明规则语法或执行正确。
- 保留命名检查：类名 `UpperCamelCase`、属性 `lowerCamelCase`、实例 `lowercase-with-hyphens` 或 `UpperCamelCase`。这是原方法命名约定；项目既有稳定IRI优先，改变显示标签不应改实体身份。实例业务键、编码和跨快照身份仍须单独定义。
- 检查命名空间IRI格式、实体中文 `rdfs:label@zh`、注释与定义。标签缺失归入文档质量；不把标注要求当作OWL逻辑公理。按声明的项目命名约定报告例外。

### 实际语法与规则结构检查

在 `Ontology/Ontology-tools` 工作目录，已按工具格式装配好独立规则包时：

```powershell
python -B -X utf8 -m ontology_tools inspect --package <本地规则包> --output <新的检查目录>
```

命令中的占位符必须替换。`inspect`按包中实际 profile 检查；默认 `local-rules-v1` 仍拒绝其支持范围以外的OWL公理，协同配置另按[投影契约](../../../Ontology-tools/PROJECTION.md)检查。原生复杂OWL可用 `owl-dl` 严格解析/profile检查，分类导出用 `owl-infer`；语法可读不代表推理已完成。格式转换脚本也可重解析指定RDF文件，但不验证SWRL变量语义。

## 2. 语义一致性

逐项检查类层次、互斥、公理、属性约束和具体事实：

| 项目 | 正确检查与解释 |
|---|---|
| 类继承循环 | 遍历所有父边，识别强连通关系并核对意外等价；循环本身不必然违反OWL，也不应只走第一个父类 |
| 多继承 | 检查各父类继承的互斥、限制与定义，不因父类数大于1就判错 |
| 不相交类 | 检查继承和等价后的隐含成员冲突；只比显式 `rdf:type` 会漏检 |
| 属性domain/range | 是类型推断，不是必填/值类型的闭世界验证；必填、唯一、数据类型、允许类由SHACL核验 |
| 功能性、基数、同一/不同个体 | OWL不默认唯一名称，基数冲突需考虑 `sameAs` 与显式不同关系；实际推理器判定 |
| 不可满足具名类 | 类被迫为空时，本体未必全局不一致；单独报告该类集合，排除内置 `owl:Nothing` |

以 `Ontology/Ontology-tools` 为工作目录：

```powershell
python -B -X utf8 -m ontology_tools owl-dl --ontology <TBox文件> --facts <ABox文件> --output <新OWL检查目录>
```

多个领域重复传入 `--ontology`。TBox-only与TBox+ABox可分别运行以定位问题。**不向该入口夹带SWRL**，它不执行规则；包含SWRL的集成文件须回到已明确的源模块选择检查范围。导入映射、状态、超时、依赖与证据见[OWL-DL使用说明](../../../Ontology-tools/OWL-DL.md)。

Protégé人工复核：加载同一份本地模型/导入闭包，选择实际支持目标公理的推理器并启动，核对一致性、不可满足类和推断分类；Ontology Metrics用于规模统计，不是通过证明。菜单随安装版本不同，记录实际版本与所选reasoner。**StructuralReasoner不能代替完整DL一致性检查**。

## 3. 规则正确性与独立测试

每条适用规则应有单元案例。记录规则IRI→案例IRI→预期→实际结果，而不是用测试类名正则推算覆盖。共享[规则设计手册](../../ontology-inference-design/references/inference-workflow.md)规定前提、回译和数值口径。

| 案例类型 | 预期检查 |
|---|---|
| 正向 | 满足全部前提，推导指定结论和类型；比较完整值集合 |
| 反向 | 明确不满足必要前提，不新增该结论；不把未推得解释为现实否定 |
| 缺失 | 缺输入时按shape阻断或保持未知；由项目契约明确，不能默认当0 |
| 边界 | 严格大于/大于等于的阈值两侧和等值，零/负数/极端值、类型错误 |
| 组合 | 多规则共同命中、重入、重复事实、多值属性、互斥结论和固定点终止 |

EOQ合成示例作为**设计用例**：`D=120, S=500, H=3000`，独立数学预期为 `sqrt(40)`；不能在未执行推理处留下 `...` 却断言成功。缺参数不得臆造结果，`H=0`须阻断除零；`D=0`是否允许、是否产0须由业务来源规定。精度与舍入由来源和后端契约确定，不得默认套用固定百分比容差。支持计算的后端必须实际执行算术/开方后再对比；当前 `local-rules-v1` 不支持该计算，不应写通过案例。

[计算协同配置](../../../Ontology-tools/CALCULATION.md)支持二元四则、显式舍入和基础日期，但没有开方，仍不能完整执行上述 EOQ。对其声明的能力，另测绑定、新值候选、带时区同值与 UTC 工作视图、计算反馈 HermiT、资源停止和重放；不要把扩展函数存在当作整条业务公式已执行。

上述限制属于旧 `hermit-swrl-calculation-v1`。[结构化公式配置](../../../Ontology-tools/FORMULA.md)另提供RDF表达树求值合同；若其当前实现支持目标函数，应实际读取核验后的表达树运行独立算例，不能仅据新配置存在宣称该公式已执行。静态公式加载、完整条件/参数绑定、结果回交、失败中间值隔离和公式证据重放分别留证，全部激活公式的算例通过与SWRL覆盖单列。

`local-rules-v1` 包的独立案例示例结构（Turtle，标识均为合成演示）：

```turtle
@prefix ot: <https://w3id.org/ontology-tools#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix ex: <urn:example:validation:> .
ex:positive a ot:Case ; ot:input "inputs/positive.ttl" ;
  ot:validationExpectation "conforms" ;
  ot:expectedTriple [ rdf:subject ex:item ; rdf:predicate rdf:type ; rdf:object ex:Ready ] .
ex:negative a ot:Case ; ot:input "inputs/negative.ttl" ;
  ot:validationExpectation "conforms" ;
  ot:notExpectedInferredTriple [ rdf:subject ex:item ; rdf:predicate rdf:type ; rdf:object ex:Ready ] .
```

独立黄金预期来自来源或人工可复核计算，不能复制当前引擎输出。执行：`python -B -X utf8 -m ontology_tools test --package <包> --output <新目录>`。具体输出和协议以[工具PROFILE](../../../Ontology-tools/PROFILE.md)为准。覆盖记录保留全部适用规则、排除依据、已执行规则、正反/边界案例数、通过失败数；分母为实际规则IRI集合，零分母报“不适用”而非除零。遵守现有“所有适用规则有单元测试、实际测试覆盖率≥80%”质量要求；覆盖率不替代关键规则正确性。

## 4. 推理验证

1. 固定本体、规则、实例快照、程序与依赖版本；声明实际后端支持哪些公理和内建。
2. 原始输入先按约定SHACL校验，执行支持范围内的规则，按需后置SHACL；前后顺序写入运行记录。
3. 保存新增推导图与闭包；预期值按集合、类型、词法/数值契约比较，不能用 `graph.value` 任取一个结果掩盖多值冲突。
4. 检查意外新增/缺失、规则来源、直接前提、重复、无限生成或未到固定点；不把“无异常退出”当正确性证明。
5. 复跑冻结输入，与独立预期及既有受影响案例比较。统一 `replay` 可复核有限规则、独立OWL-DL检查/导出及协同运行，先核验快照和环境，再比较对应状态与图。已完成的不一致或不可满足结果可复现，但不能因此标为本体通过；技术失败不能当作成功重放。

原owlready2/Pellet示例的目的为“真实执行推理并收集结果”，现由已有CLI/API承担。不同引擎对SWRL支持不同，不通用地宣称选择Protégé或HermiT就能执行任意SWRL。未实现的引擎适配记 `not_run`，执行报错记 `failed`。

## 5. 集成验证

- 明确集成模式：物化合并或imports入口；核对每个模块角色TBox/Rules/ABox与加载清单。
- 递归核对导入IRI、本地路径、目标声明的本体/版本IRI及文件指纹；不能把IRI尾段拼成假定文件名。缺依赖停止该加载链，不在线兜底。
- 物化装配时隔离源文件空白节点作用域，重新解析结果，使用图同构比较预期源并集；同数量不足以证明完整。允许的头部元数据变化或有依据重写需列入差异。
- 真正语义融合则按已确认映射生成预期图，验证保留/删除/替代公理及新增蕴含；不能要求全部原冲突公理继续保留。
- 合并后对联合图实际运行DL、SHACL与规则回归。来源模型各自一致不保证合并后一致。
- 目录模板的 `integration/build-evidence.ttl` 与 `scripts/build_integration.py --check`可检查源与派生产物，脚本所在项目实际输入需先确认；它不是DL推理器。

## 报告、阻塞与复验

报告保留原模板八部分：①名称、版本、时间、输入/工具指纹；②OWL/RDF、SWRL和命名语法；③层次、互斥、属性约束、全局一致性及不可满足类；④按规则类别列总数、测试数、通过失败数和覆盖口径；⑤场景、独立预期、实际值、差异及依据；⑥导入闭包与合并完整性；⑦总体状态、限制、未执行项、建议；⑧问题位置、原因、修复与复验命令/证据。类别按实际项目，可有库存、供应商、KPI，不预填结果。

| 常见问题 | 处理及需保留的证据 |
|---|---|
| 意外层次等价 | 检查每条父边的来源，确认循环是否意图；必要时改有误的源公理 |
| 互斥冲突 | 核对显式与推导类型、身份及原事实；不能为通过而直接删除不相交公理 |
| 属性验证失败 | 分清错误值、错误shape、范围推断或缺失；放宽约束须有来源 |
| 单规则失败 | 按独立预期检查条件、类型、边界与输出，不倒改预期 |
| 推导异常 | 检查规则组合、缺口、支持范围、实际闭包和冲突前提 |
| 导入缺失 | 修复明确本地映射、文件版本和加载范围，再重跑完整受影响链 |

验收清单：语法可读；类层次意图核实；互斥/OWL DL检查完成；数据约束符合；适用规则有单元案例及覆盖证据；结果符合独立预期；导入闭包完整；装配保真；文档与本体一致；未通过项有准确状态。发现真实矛盾、规则错误、结果不符或断裂依赖时不发布“已验证通过”，保留现场后修复；用户已确认人工处置的业务缺口保持该处置。
