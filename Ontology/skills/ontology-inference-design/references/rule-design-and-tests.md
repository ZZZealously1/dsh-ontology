# 规则设计与独立测试

本参考说明规则分类、前提与结论设计、逻辑验证、语义回译及独立测试，供[推理技能](../SKILL.md)实施时使用。适用于新增、修改或排查规则；文件结构按[输出规范](../../../CONTRACT.md)落实。这里的检查项不构成新的业务阈值或审批要求。

## 1. 按规则目的选择表达

| 规则目的 | 设计对象 | 需要分开的语义 |
|---|---|---|
| 分类 | 根据有依据的条件增加类成员断言或分类代码 | 类成员、枚举个体与字符串代码须与属性类型一致 |
| 关系/属性推导 | 从同一对象或有证据的关系链增加断言 | 不能跨对象、快照或周期拼接前提；关系方向必须明确 |
| 计算 | 从已知输入计算派生值 | 公式、单位、参数域和数值实现分别核对；公式文字不等于结果 |
| 违规或预警标记 | 在条件成立时推导待复核等结论 | SHACL 输入拒绝、业务预警、动作执行是不同结果 |
| 时序判断 | 从事件或快照推导某时点的适用状态、候选动作 | 单调规则增加事实，不自动撤销旧状态、覆盖值、发送审批或执行状态迁移 |

分类是帮助审查的视角，不要求每个项目凑齐五类规则。优先用已有公理表达确切语义；只有需要规则条件时才增加 SWRL。集合聚合、闭世界否定、优先级和流程控制须有单独的项目执行契约，不能默认由 SWRL 提供。

## 2. 将业务条款逐项变成前提和结论

在现有规则注释、`provenance.ttl` 和领域说明中保留下列信息，不另建一份手工维护的业务条件源：

- 规则 IRI、负责领域、能力问题、条款位置、来源版本/有效期、适用对象与状态。
- 前提所用类、属性、关联键、对象粒度、时间窗口、单位及数据完整性范围。
- 条件之间的合取、边界包含性、例外、已确认的未知/冲突/人工处理方式。
- 结论的精确主语、谓词和对象，以及它表示派生事实、候选状态还是确认后的状态。
- 需要的后端原子/函数、依赖规则或公理、独立案例 ID 和尚未解决的缺口。

执行一次语义回译：来源条款 → 形式规则 → 自然语言解释 → 条款逐项对照。检查漏掉的必要条件，也检查额外条件是否无依据地缩小适用范围。规则前提足以推出结论，不代表业务上只有这组前提才能得到该结论；不要把单向蕴含误写成双向等价。

每个变量的绑定来自具体个体、关系或已支持的计算结果。多个对象即使属于同一工单，也需要明确关联条件；不能只因字段名相同而连接。遇到来源冲突、未确认的阈值、舍入或审批，不补默认值，保留已确定的人工处置或待确认状态。

规则候选与实际执行规则按输出规范隔离：状态注释不是禁用开关。未决候选可以留在设计/来源记录中；若保存为真实SWRL草稿，必须证明实际加载器未将它放入本次规则图。缺少排除机制时停止受影响的运行，不把注释为draft的规则交给忽略该注释的后端。

## 3. 计算规则的核对顺序

1. **公式和适用条件。** 记录项目实际采用的公式来源及定位、符号定义、假设和使用范围。公式来自教材或标准的说法若无法定位，只能列为待核实，不能作为已验证依据。
2. **量纲和输入域。** 核对输入/输出单位及期间、分母为零、负值、缺失、溢出和函数定义域。正数、非负数等限制须来自具体公式及业务语义；不可给所有数值统一添加 `> 0`。
3. **数值表示与后端。** 金额采用明确的十进制表示；记录后端内部运算类型、函数 IRI、绑定方向及异常行为。开方或非终止除法即使输入为 decimal，也需定义输出精度和误差处理。
4. **舍入与比较。** 写清位数、模式、发生阶段、单位转换、分摊尾差及比较容差的依据。若容差适用，区分绝对/相对误差及零附近行为；没有依据不套用小数两位、5%或其他通用默认。
5. **独立算例。** 从已知例题、人工核算或独立计算过程获得预期，实际引擎必须读取规则并生成结果。测试只在 Python 中重算公式而未执行规则，不能证明 SWRL 正确；算例也不能覆盖公式全部适用条件。

采用[结构化公式配置](../../../Ontology-tools/FORMULA.md)时，第5项由实际后端读取唯一RDF表达树求值，不强制把公式转换成SWRL运算链。每个激活公式都须有独立算例并通过，另测单位、参数域、条件缺失、错误对象/工况、依赖环和失败结果不泄漏；公式执行覆盖与SWRL规则执行覆盖分开报告。

算例应同时检查值、类型、单位、对象和来源。使用实际允许的精确比较或容差比较，不能以“有值”“不小于零”替代一个确定的预期。若尚无可靠数值后端或舍入口径，交付相应草案/人工项；不把手算值写进事实图冒充推导结果。

## 4. 规则组合、依赖与状态

按规则读取和产生的谓词/类建立依赖关系，审查推导链、共享中间结果、同时命中、重复结果和冲突。依赖成环不必然无效：有限事实上的正向规则可能收敛；不断生成新数值或个体的扩展可能不终止。按实际后端验证固定点、停止条件和资源限制，超时必须报告未完成，不能当无匹配。

书写顺序不是通用优先级。业务需要互斥、覆盖或优先裁决时，用有依据的应用规则显式处理；不能仅调换规则顺序消除冲突。推理出新状态后原状态可能仍存在，应使用带时点的状态记录或明确的候选状态关系。新增实例、撤回断言和动作调度是额外能力，不能从普通 SWRL head 自动获得。

组合测试既看最终结论，也看关键中间事实和不应出现的结论。若多条规则可独立得出同一结论，破坏其中一条前提并不保证整个模型不再蕴含该结论：规则隔离测试与整包黄金测试分别确定范围，不能把合法的另一条推导判成误触发。

## 5. 先固定预期，再执行比较

每个案例在 `tests/cases.ttl` 关联能力问题、规则/公理、依据和输入；按运行器实际支持的协议保存预期，不假定自定义词汇已被实现。逐条检查下列情况是否适用，并说明未覆盖项：

| 场景 | 预期表达 |
|---|---|
| 全部前提成立 | 指定对象产生指定类型、关系或值；输入中未预写该结论 |
| 逐项破坏必要前提 | 在声明测试范围内不推导指定结果；不是把未知当逻辑否定 |
| 等于阈值与两侧、跨期间/生效期 | 独立的包含/排除边界；具体值来自来源和数据类型 |
| 缺值、非法类型、函数定义域之外 | 确切拒绝、未知或人工状态；不使用“无值或任意非负值均通过” |
| 同名异物、错误边方向、跨快照拼接 | 不产生跨对象结果，或按输入契约明确拒绝 |
| 多规则、链式推导与依赖环 | 预期中间/最终结果、冲突处理和实际终止状态 |
| 不支持表达、加载失败或执行异常 | 明确失败/未支持；不能作为负向规则测试通过 |

比对实际图中的完整目标值集合、类型及禁止结果，避免 `graph.value()` 任取一个值漏掉额外错误断言。需要验证新增推导时同时保留运行前输入和运行后结果；纯查询任务按查询集合与口径验收。空负例只能在已证实加载和执行成功后被解释为预期的“不推导”。

为所有适用规则设计单元测试，并达到至少 80% 的实际规则执行覆盖率。项目执行前固定适用规则 IRI 分母与排除理由；成功执行且与独立正向预期一致、有实际产物证据的规则计入分子。工具不支持、遗漏加载或缺输入的适用规则仍属于未覆盖，不能从分母删除。没有规则时说明不适用，没有执行证据时不能声称达标。

测试文件里出现类名、函数名或注释不等于规则执行；后端无轨迹时可用声明范围的规则隔离/独立蕴含测试，报告其证据范围，不伪造命中率。所有规则有测试设计、执行覆盖率、正向/反例/边界、公理与能力问题覆盖分别报告。达到 80% 不能豁免失败或替代边界与组合验证，未覆盖 IRI 及原因必须披露；这一质量门槛不授权套用 5% 数值误差或任何业务阈值。完整口径见[验收清单](../../ontology-validation/references/acceptance-checklist.md#覆盖记录)。
