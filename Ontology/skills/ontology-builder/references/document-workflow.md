# 文档建模完整流程

本流程覆盖文件抽取、补充资料、概念/属性/规则、OWL生成、集成、检查、测试和说明文档十阶段。按任务进入受影响阶段，已完成的工作不重复索取；局部变更保留影响分析和回归。数据与输出规则见[CONTRACT](../../../CONTRACT.md)。

## 1. 文件识别与内容提取

登记原文件名、实际格式、来源ID、版本、生效期、文件指纹和可用解析工具。先读文档目录或工作表清单，再检查实际内容覆盖范围。

| 输入 | 提取与定位 | 输出内容 |
|---|---|---|
| PDF | 目录、页、章条、正文、表格、图注；扫描件记录OCR | 原文片段、结构、条件、提取疑点 |
| Word | 标题层级、段落、表格、样式、列表、脚注、修订 | 条款路径、表格位置、术语与流程 |
| Excel | 全部相关Sheet、列头、原值、类型、单位、公式/缓存 | 字段契约、记录与单元格定位 |
| CSV | 编码、分隔符、列头、数据行和引用规则 | 字段与行记录；保留前导零和空值 |
| JSON等既有结构化输入 | 对象路径、数组、键值、类型和记录身份 | 内存解析后映射到RDF；不生成JSON中间文件 |
| TXT/Markdown | 编码、标题、行段、实体候选、表格和上下文 | 可定位的素材、候选概念和关系 |

识别标题以理解领域，章节以理解分类候选，表格以识别属性/实例，术语定义以核对概念，流程以提出规则，数值描述以登记约束。不能仅凭标题或词性直接确定模型。图表、上标、单位、脚注和例外会改变结论时必须一起提取；无法读清的内容保留缺口。

按当前可用解析器与OCR能力处理文件；不支持的格式或识别失败范围明确记录。实际读取范围记录到来源证据，不能把一张Sheet或几页的成功当作整份资料已处理。

## 2. 领域资料查找

先建立明确缺口，再查已提供资料中的术语表、定义和引用，最后考虑任务允许的补充来源。专业术语、缩写、行业名可以构成检索词，例如材料出现EOQ、ABC分类或核电术语，只说明应核对这些词，不授权增加库存政策或核安全规则。

| 缺口 | 可用检索主题 | 采用前核对 |
|---|---|---|
| 概念定义 | 领域＋概念＋定义/术语标准 | 对象范围、成员条件、语境 |
| 属性类型 | 领域＋属性＋数据模型/类型 | 单位、粒度、可空、精度 |
| 关系含义 | 实体A＋实体B＋关系/流程 | 两端身份、方向、时间和角色 |
| 公式 | 规则名＋公式/参数/条件 | 公式依据、单位、输入域及例外 |
| 分类标准 | 领域＋分类标准 | 适用对象、版本、边界与全集 |
| 枚举范围 | 属性＋取值范围 | 完整性、未知/其他值和有效期 |

可复用来源类型包括正式标准（国际/国家/行业）、专业机构资料、研究文献、技术文档和既有本体。LOV、BioPortal、Schema.org、DBpedia可作为查找途径，只有任务允许外部读取、工具实际可用且内容适用时才访问。选择当前环境实际具备的搜索/读取接口。

可按“输入文档→国家/行业标准→权威网站→开源本体→其他资源”查找补充资料。来源优先级须结合发布主体、版本、生效期、适用范围和用户确认；百科内容不能仅因被列为示例就视为规范依据，先后顺序也不能自动解决冲突。

建立原词—别名—定义—来源—适用范围—目标IRI—采用/排除/待确认理由的术语对照。对补充资料核对可信度、可用的交叉证据、上下文语义、一致性和缺口是否真正解决。没有资料时继续确定部分，不用通用公式或枚举补成项目制度。

例如，只有“名称、数量”两列的备件清单不能证明供应商、价格、安全库存、EOQ及预警规则都属于当前项目。候选保留在设计记录，经依据核对后才进入模型。

## 3. 概念提取与层次构建

1. 从重复名词、术语定义、表头和章节提出核心实体候选，结合能力问题确定类、个体、角色、状态、字段或文档结构。
2. “是一种/分为”需验证每个子类成员都是父类成员；“包括”需区分成员、组成和分类；“属于/关联/具有”需核对两端与关系含义。
3. 状态、等级、分类等固定取值可作为枚举候选；值的穷尽范围有来源，未知值有明确处置。
4. 同义词经定义核对后复用身份；同名异义分开。为候选提供合理实例、反例、中文定义、来源和取舍理由。

通常优先简洁层次；层数由概念关系与可读性决定，不设统一层数。多重继承有语义依据即可使用；同层类不自动互斥。声明 `owl:disjointWith` 前检查成员条件与时间状态。抽象类可作为设计意图；OWL没有通用禁止直接实例化的abstract开关，有输入限制需求时显式建shape。

## 4. 属性体系设计

| 关系意图 | 命名示例 | 必须核实的特征 |
|---|---|---|
| 归属 | belongsTo、hasParent | 是否至多一个归属、是否共享目标；不能从名字推出逆函数性 |
| 组合 | hasPart、consistsOf | 部分关系的粒度和传递条件 |
| 关联 | relatedTo、associatedWith | 关系是否真的双向对称 |
| 因果 | causes、leadsTo | 方向、时间及是否允许互相作用 |
| 时序 | precedes、follows | 相对时间、传递性/非对称性的适用范围 |

逐属性记录中文含义、IRI、domain/range、主体→客体例子、角色和时间范围、逆属性/子属性及特征依据。inverseOf两端都明确声明，函数性放在真实“至多一个值”的方向；多个domain通常是交集语义，跨域可选类型要显式定义所需表达。

| 数据类型意图 | 命名示例 | 需落实的约束 |
|---|---|---|
| 标识 | hasId、hasCode | 业务键、作用域、编码、碰撞检测；OWL身份推断与数据唯一校验分开 |
| 名称 | hasName、hasLabel | 标签语言、别名、名称不等于身份 |
| 数值 | hasValue、hasQuantity | 类型、单位、精度、范围及边界依据 |
| 日期 | hasDate、hasTime | 数据类型、时区、事件/快照/有效期 |
| 状态 | hasStatus | 枚举、未知值、历史状态与当前状态 |
| 描述 | hasDescription | 文本语言、来源和格式 |

原始属性和派生结果区分。基数、必填、唯一、格式及枚举的数据验收放入SHACL或明确的校验步骤，不把OWL domain/range当作表单检查器。参考[数据契约](../../business-ontology-design/references/data-contract.md)。

## 5. 推理规则设计

规则按推导、计算、约束标记、分类和时序需求归类，逐条形成业务含义、来源、对象、前提、结论、例外及独立预期。参考材料中的许可证、EOQ、库存与ABC规则均为模式示例，不是本项目政策。

使用[规则设计](../../ontology-inference-design/SKILL.md)完成原文→形式化→中文回译。先声明谓词，核对变量绑定、对象关联、类型、单位和边界。计算规则缺舍入、窗口、尾差或有效输入域时保留缺口；时序规则不能把状态候选当成已经完成的外部动作。

## 6. 生成OWL与原生规则

新项目默认类名UpperCamelCase、属性名lowerCamelCase，为类/属性提供中文标签与说明；实例名采用可维护的英文标识或稳定编码，风格与业务身份分开。已有合法IRI不因风格不同而重命名。`example.org`只用于示例，正式命名空间由项目稳定身份契约决定。

类、对象属性、数据属性、限制、公理、枚举及实例表达见[OWL/SWRL参考](../../../references/owl-swrl/index.md)。`.owl`和`.swrl`使用RDF/XML，`.ttl`使用Turtle；OWL/XML是另一种序列化。SWRL必须包含真实 `swrl:Imp`、原子、变量和RDF列表；可读公式是说明视图。

形成领域TBox、独立ABox、规则、SHACL、provenance和mapping。脚本可以辅助首次生成和重建，但交付后的OWL/SWRL是语义维护源；不并行维护一套Python业务条件。所有来源、版本、角色及依赖写入加载清单。

数量较多的科学/工程公式可按[结构化公式合同](../../../Ontology-tools/FORMULA.md)建立独立 `formulas/<domain>.ttl` 静态目录，以RDF表达树为唯一公式执行源，保留原LaTeX、符号、输入/输出、单位、必要条件和来源。批量抽取先登记候选/不支持/冲突，不能未经核验激活；OWL/SWRL维护诊断与适用性，SHACL约束参数关联。旧规则计算配置继续按原合同使用，不批量改写已有模型。

## 7. 本体集成

存在原模型时，先固定版本并检查命名空间、IRI重定义、概念同义/歧义、规则引用和依赖。需要语义对齐时先用[融合方法](../../ontology-fusion/SKILL.md)作出有依据的决策，再装配文件；新项目则建立根入口与清单。

| 模式 | 实现与验证 |
|---|---|
| 物化集成 | 从明确TBox/规则源构建一个图，保持空白节点作用域与RDF列表；核对源覆盖、图同构及预期推导 |
| imports入口 | 声明导入IRI，提供显式本地映射，核对所有传递依赖；入口文件自身不代表完整内容 |

默认动态ABox不写入集成模型。记录实际运行器读取的文件与规则，文件名 `merged_ontology.owl` 不证明已合并。已有包不能在未知版本上直接覆盖；修复回到原生源，再重建派生入口。

## 8. 一致性与结构检查

按[验证技能](../../ontology-validation/SKILL.md)分别执行：

- RDF/XML/Turtle解析、IRI与命名约定、声明及引用完整性。
- 类层次和定义核对；继承环可能形成等价，应检查是否符合设计，不一概判不一致。
- OWL DL profile、全局一致性及具名类可满足性；含实例的互斥矛盾和基数限制由真实推理器检查。
- 数据类型、必填、枚举、键、关联范围等SHACL检查，明确输入图与推理选项。
- SWRL结构、变量、安全性、类型及真实后端能力；OWL检查不冒充SWRL运行。

用[离线OWL DL工具](../../../Ontology-tools/OWL-DL.md)时显式选TBox/ABox，不能输入含SWRL的默认集成图后声称全包执行。报告全局结论与不可满足类，加载/环境失败记录未知结论。

## 9. 规则测试

每条适用规则至少设计正向、反向与边界，并按依赖和共享结果补充组合用例。反向案例要证明引擎正常完成且目标未新增，不能用加载失败当“不命中”。边界包括精确端点、端点两侧、零/空/未知、类型错误、跨对象/周期及例外，按实际条件选择。

先从业务来源形成独立预期，再运行原生规则，比较完整结果集合并保留输入、输出、轨迹及日志。Python测试类仅组织测试；`pass`、省略号、手工算式或复写规则条件不构成引擎验证。重复运行检查固定点/幂等，不能只比较三元组总数。

所有适用规则具备测试，实际执行覆盖率按[验收清单](../../ontology-validation/references/acceptance-checklist.md)记录；80%是已有质量门槛，不豁免失败，也不是业务容差。缺引擎支持的规则列为未执行，不能删规则提高通过率。

## 10. 完整说明、目录与交付

使用[完整说明模板](full-domain-document.md)覆盖全部类、属性、规则和使用指南；统计来自实际图且说明计数范围。每条复杂规则包含完整语法阅读视图、计算参数/算例、验证方法与相关规则。实际运行结果与文档示例分开。

```text
ontology/
  subontologies/<domain>_ontology.owl
  rules/<domain>/<domain>_rules.swrl
  data/instances_<domain>.owl
  integration/load-plan.ttl
  integration/merged_ontology.owl
  docs/<domain>_本体说明.md
  tests/...
  shapes.ttl
  provenance.ttl
  mapping.ttl
```

README、运行期SKILL、验收记录、真实命令和指纹按中央规范补齐。测试放在包内 `tests/`；运行输出放在输入包外的新目录，保持源文件不变。

## 常见问题与处理

| 问题 | 处理 |
|---|---|
| 概念重复或命名混乱 | 先建立术语与IRI对照，证据充分才合并身份 |
| 前提不完整、边界遗漏 | 回译条件与例外，补独立反例再执行 |
| 导入循环与冲突 | 核对加载闭包及版本；意外依赖回到源模块修复，不凭循环直接断定OWL不一致 |
| 只做正向测试 | 补反向、边界、跨对象和适用的组合案例 |
| 概念或命名空间冲突 | 已有资料可裁决时记录理由并处理；决定性歧义待确认，不重复询问已确定事项 |
| 检查或测试失败 | 保留失败证据、定位来源/模型/引擎问题，修复后新开运行；不以改报告冒充通过 |
