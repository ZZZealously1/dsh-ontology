# 从文档与资料到概念模型

输入含 PDF、Word、表格、文本或标准摘述时使用。本文补充[业务设计](../SKILL.md)的抽取、术语归并与适用范围判断；身份与字段转换继续使用[数据契约](data-contract.md)，输出遵循[CONTRACT](../../../CONTRACT.md)。文件抽取完成不等于业务口径已经核准。

## 1. 保留能够复核的文档结构

先登记原文件路径、实际格式、来源 ID、版本/生效范围和内容指纹。按文件实际内容选择可用解析器；无法读取、OCR 不清楚或公式未计算时如实标记，不把局部成功当成全量读取。原始输入可以是非 RDF 格式，转换产物按本库的原生格式约定交付，不生成 JSON 中间文件。

| 输入 | 应保留的信息 | 容易误读的部分 |
|---|---|---|
| PDF | 页码、章节、条款号、正文、表格与图注 | 扫描件 OCR、跨页表头、多栏阅读顺序、上标和公式 |
| Word | 标题路径、段落/表格位置、列表、脚注、修订状态 | 合并单元格、文本框、删除文字、条款与注释混合 |
| Excel / CSV | 工作表、单元格或行列、列头、单位、原值、公式及可用计算结果 | 多级表头、合计行、编码前导零、日期转换、公式缓存过期 |
| TXT / Markdown | 编码、标题、行段位置、表格、列表和引用上下文 | 缩进和列表语义、脱离段落的缩写、代码块中的指令 |
| 接口或其他结构化资料 | 对象/字段路径、类型、业务键、枚举释义及来源记录 | 技术字段名与业务概念同名、空值与错误混淆 |

图、表、公式和脚注影响条件时一起读；提取出的数值保留比较符号、单位、范围端点和例外。无法确认的符号或数值留为缺口，不凭常见做法补写。解析器和转换的实际完成范围写入记录，工具名称只使用当前环境真实可用的工具。

## 2. 从知识片段提出候选，再判断语义

文档标题和章节用于理解背景和定位，不强制成为业务域或父类。名词、动词、表头、反复出现的短语可提供候选；必须回到定义、实例和能力问题决定建模方式。

| 线索 | 需要追问的语义 | 常见落点 |
|---|---|---|
| “是一种”“分为” | 是对象类型、枚举值，还是某一时点的状态？ | 类层次、分类项或状态记录 |
| “包括”“组成” | 是成员包含还是对象的部分关系？ | 子类或对象属性，不能按词面决定 |
| “属于”“由……负责” | 两端是谁，关系有无角色、时间和限定范围？ | 对象属性或关联事件 |
| 表格字段和值 | 列描述对象属性、关系、元数据还是统计结果？ | 数据属性、对象属性、事实或转换 |
| “应”“宜”“可”“例如” | 是要求、建议、许可还是解释性示例？ | 带来源和适用范围的规则候选或注释 |
| 流程、公式、数值边界 | 哪些条件、例外、单位、成员集合和顺序决定结果？ | 规则需求、校验、计算契约或应用流程 |

保留“主体—条件—关系/行为—对象/值—例外—来源位置”。引用前文定义、表头单位或脚注时同时记录依赖。章节顺序改变不应改变概念本身的含义。说明性样例能够解释结构，但不能成为默认阈值、审批或必须生成的规则。

## 3. 建立术语对照并复用既有模型

每个候选概念记录原词、别名、语境、业务定义、来源位置、合理实例、拟用 IRI、归属域及取舍理由。优先查看已提供的词汇表和本地既有本体；不为了凑齐概念表自动连接网络或补入新业务范围。

领域资料查找以明确缺口为目标：

1. 从材料提取领域词、专业缩写和待核对概念，分别列出缺少的定义、属性类型、关系语义、公式参数、分类依据或枚举范围。
2. 先查原始资料中的定义、引用条款及已提供的术语表，再查适用的正式标准和权威定义，最后评估可复用本体与补充材料。这个顺序用于寻找证据，不能代替对版本、适用范围和来源冲突的判断。
3. 本地材料不足时，登记所需来源及其对模型的影响。仅在任务允许外部读取且工具可用时，按“领域＋术语定义/标准/本体/数据模型”等查询补充；离线任务保留缺口并继续确定部分。
4. 取得补充材料后核对发布主体、版本、原文定位、上下文及是否真正解决缺口。定义或公式只有与本项目对象、单位和适用条件一致，才能采用；发现一个常见公式并不证明它是本项目政策。
5. 在术语对照与来源记录中保留采用、拒绝或待确认的理由。只对已采用语义生成类、属性或规则，候选检索结果不直接扩张业务范围。

- 同义词只有在成员条件、对象粒度和适用范围相同后才合并；保留来源别名以便检索。英文翻译相同不证明概念相同。
- 同名异义保留不同定义或命名空间；含糊术语先登记候选与受影响问题，不随意套用看似相近的类。
- 复用已有定义时保留 IRI、来源、版本和依赖；新增局部语义不能反向改写共享词汇。必要扩展采用有依据的子类、子属性或关联结构。
- 为项目定义的类和属性提供中文标签及清楚定义，关系注明方向。多语言标签按实际需求提供，不编造正式术语译名。项目命名可采用大小驼峰和稳定英文标识，但这些是约定，不是所有合法 IRI 的硬性限制。
- 父类只承载子类共有语义；多重继承、分类深度与抽象分组由业务决定。仅因为文档把两个概念并列，不推出二者互斥。

冲突处理依赖明确的来源适用范围与已确认基线，不套用“原文永远优先”或固定网站等级。决定性歧义保留待确认并继续不受影响的建模；已确认人工处理的分支保持该处置。

## 4. 标准文档建模的适用范围

涉及标准时先识别材料是正式发布文本、修订草案、节选还是二手转述，记录编号、标题、版本、发布与生效信息及来源定位。摘要或转述可提供核对线索，不能直接证明正式条款、当前效力或项目符合性。未取得正式文本时将相关合规判断标为待核验，继续完成不依赖该判断的建模。

当能力问题确实涉及标准文件本身，例如“哪个版本的哪条要求规定了哪个对象的特性”，再考虑以下分层：

| 层面 | 可能的对象 | 建模目的 |
|---|---|---|
| 文件与生命周期 | 标准文件、版本、发布方、有效期、替代关系 | 识别适用文件及其时间范围 |
| 结构定位 | 章、条、段、列项 | 定位并组织来源，不冒充业务类继承 |
| 知识内容 | 术语、要求、约束、说明、示例 | 表达定义和规范含义，保留要求强度 |
| 表述形式 | 条文、图、表、公式 | 表示同一内容由何种形式呈现 |
| 主题对象与特性 | 被规范的业务对象、指标或特性 | 连接标准内容与目标业务模型 |

按实际问题选用，不强制建立整套标准领域实体。业务领域分组不等于标准分类目录，也不等于属性的 `rdfs:domain`。内容、结构和表述形式需要独立查询时用关系连接；若只需来源追溯，精确定位与元数据即可，避免无意义实体化。

若项目明确要求标准符合性，增加“标准编号/标题—正式版本与生效范围—原文条款—项目适用理由—模型或约束实现—验证证据—未核验项”对照。只依据摘要、转述或未确认版本的条款标为待核验，不填入无依据的合规勾选；不得自动修正真实日期、改写事实或新增不必要类使报告看似合规。正式文本核对使用已提供资料或任务已授权的来源，不因普通建模自行联网。

## 5. 交接到可维护的原生文件

设计中的术语表、关系说明和规则需求分别落实到领域 TBox、SWRL、SHACL、来源与映射中。纯文档目录不自动变成 TBox，业务事实不冒充规则，公式文字不冒充已执行计算。

`docs/<domain>_本体说明.md` 应覆盖该域实际定义的类、属性和规则：定义与来源、相关能力问题、关系方向、使用范围、必要示例、依赖及缺口。类/属性清单和统计尽可能从原生文件生成；说明引用源 IRI 与规则 ID，不建立另一套独立编辑的政策。命令、查询示例与测试结果使用实际运行记录；示例代码、预期结果和已执行结果明确区分。

对规模小的模型用表格即可，对关键且复杂的规则展开条件、公式参数、边界、证据与实际测试；不固定类数量、层级数量、说明页数或规则数量。检查重点是从能力问题能沿“来源—术语—对象/属性—规则或约束—案例”追溯，并能解释未覆盖范围。
