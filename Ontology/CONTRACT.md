# ontology 目录输出规范

本规范落实用户指定的文件结构、原生格式和执行证据要求，与建模流程配套。整体流程与建模要求见[总入口](skills/ontology-builder/SKILL.md)；本规范不另立建模主流程，不把某个执行器的规则子集当作通用标准。具体项目须声明实际后端、格式细节和支持范围。

可选择本目录下的 [Ontology-tools](Ontology-tools/README.md) 作为已实现的本地工具，但须分别核对 [有限规则](Ontology-tools/PROFILE.md)、[独立 OWL DL](Ontology-tools/OWL-DL.md)、[有限投影协同](Ontology-tools/PROJECTION.md)、[计算协同](Ontology-tools/CALCULATION.md)或[结构化公式协同](Ontology-tools/FORMULA.md)的实际支持范围。通用内核跨项目复用，项目继续交付本体、规则、形状、事实、映射与独立案例；此选择不意味着其他项目自动具备相同执行能力。

建模流程见[总入口](skills/ontology-builder/SKILL.md)，共享原则见[common_rules.md](common_rules.md)。可复制的文档和原生格式参考见[模板目录](templates/README.md)；模板自身是草案，不是已验收的业务包。

## 1. 单包结构与领域组织

新项目默认采用领域分层布局，所有本体产物放入指定项目下的 `ontology/` 目录，该目录即包根。若指定路径已经指向 `ontology/`，直接使用，不再嵌套同名目录。`<domain>` 是项目内稳定领域标识；一个领域可以覆盖多张表，单领域项目只需一组文件。领域边界、共享概念与跨域关系的判断见[领域组织方法](references/domain-organization.md)。

```text
ontology/
├── README.md                 # 适用范围、后端、依赖、命令、缺口
├── SKILL.md                  # 智能体运行步骤
├── subontologies/
│   └── <domain>_ontology.owl  # 领域TBox：类、属性、公理
├── rules/<domain>/
│   └── <domain>_rules.swrl    # 该领域原生SWRL规则
├── formulas/<domain>.ttl     # 可选：结构化公式目录，独立静态角色
├── data/
│   └── instances_<domain>.owl # ABox：实例和事实快照
├── integration/
│   ├── load-plan.ttl          # 领域、模块、依赖、角色和本地加载清单
│   └── merged_ontology.owl    # 从模型和规则源构建的集成入口
├── docs/
│   └── <domain>_本体说明.md   # 范围、概念、规则、数据与使用说明
├── shapes.ttl                # SHACL约束
├── provenance.ttl            # 来源、规则依据、确认、冲突与待确认项
├── mapping.ttl               # 数据映射契约
├── tests/cases.ttl           # 独立黄金预期
├── tests/inputs/*.ttl        # 案例输入
├── runtime/                  # 所选后端入口/适配器及必要代码
├── runtime.ttl               # 后端需要时提供的原生配置
├── requirements.txt          # Python后端使用；其他后端提供对应依赖文件
├── acceptance.md             # 当次验收结论和证据位置
└── manifest.sha256           # 冻结清单
```

- 文本UTF-8；新文件 `.owl`、`.swrl` 固定RDF/XML，`.ttl`固定Turtle。测试夹具可用Turtle。既有资料先识别实际序列化；遇到Turtle内容的 `.swrl` 时，记录原文件格式并进行可核验转换，不能只改后缀。使用真实RDF/SWRL结构，不生成JSON、不把JSON嵌入RDF或改后缀，不另维护一份业务条件表。
- 可执行包必须有实际入口、依赖/版本和安装前提；外部安装的后端写清获得方式，不伪装为已随包提供。不需要的依赖文件不生成；缺后端时交付模型草案并明确缺项。
- 使用共用运行器时可以省略重复的 `runtime/` 代码，但须写明实际工具路径、版本、依赖及可复现的调用方式；要求独立搬运的包应随包提供必要运行器，或明确离线获取前提。
- 无SWRL规则的纯OWL推导或纯查询项目可省略相应规则文件，并在加载清单说明不适用；不能用空文件冒充规则能力。
- 运行证据可在冻结前放入 `validation/`，或由 `acceptance.md`引用包外明确位置。后续运行写包外新目录，不修改冻结包。
- 多领域项目增加对应领域文件；需要复用的基础词汇按实际职责形成共享模块，跨域关系和规则有明确归属与依赖。不能把按类/属性分文件称为已完成业务域划分，也不强制每个领域拥有不同命名空间。
- 来自文档或知识库的项目，在 `provenance.ttl` 保留抽取/检索来源及定位；详细检索记录或获准保存的片段可按需放 `sources/`，使用说明过的RDF词汇或原始文本格式。没有此需求时不生成空目录。输入资料可以是PDF、DOCX、表格等，进入推理前须有明确抽取、映射和校验；输入格式不改变原生语义交付要求。

### 源文件与集成入口

`subontologies/` 和 `rules/` 是模型与规则的维护源；`data/` 是独立事实源。默认 `merged_ontology.owl` 是模型与规则的物化集成结果，供查看及后端加载，不是第二套手工维护的政策。提供实际构建命令、源文件指纹、构建器版本与等价检查，源有变化后重建；不手改合并文件后让源文件失配。

默认集成结果不包含动态ABox。运行时由加载清单指定 `data/` 快照或本次事实输入；若交付含ABox的离线展示快照，单独命名并明确其时间、数据范围和用途，不让它成为后续推理的默认事实。文档或文件名含“merged”不证明已经载入全部规则和实例。

可选纯 `owl:imports` 入口必须明确标为“导入入口”，交付固定版本的IRI到本地文件映射，验证离线导入闭包和实际后端的加载行为。缺模块或映射失败时报告缺项，不自动访问远程IRI。规则与实例未被导入时，须由运行器显式加载并留证。

`integration/load-plan.ttl` 至少列出：领域ID/范围及说明位置，模块角色（TBox/规则/ABox，适用时另列FormulaCatalog）、相对路径、实际格式、可用的本体IRI/版本、依赖、入口模式、是否含ABox和运行时事实选择方式。路径限定包内；构建和加载日志记录各角色实际读取的文件与指纹。清单是项目契约，不能假定任何引擎天然理解自定义RDF词汇。

### 既有扁平包与工具兼容

既有 `ontology.ttl + rules.swrl + inputs/facts.ttl` 布局继续可用，不为本次方法调整批量迁移已有项目。新项目如因后端采用扁平部署布局，须说明该选择与领域源文件的映射。

`Ontology-tools` 的包执行配置均按固定扁平路径读取，不解释本规范的领域加载清单；领域源须通过实际实现并验证的适配生成运行包，保留模型/规则/事实角色及独立案例。默认 `local-rules-v1` 拒绝 `owl:imports`；显式选择 `hermit-swrl-projection-v1` 或 `hermit-swrl-calculation-v1` 可通过包内 `imports-map.ttl` 加载本地模型导入。`hermit-swrl-formula-v1` 依其专用合同另加载扁平 `formulas.ttl`，领域源为 `formulas/<domain>.ttl`；适配器须另行证明公式图等价，不把静态公式混入动态事实。旧配置合同不变。独立 [owl-dl / owl-infer](Ontology-tools/OWL-DL.md)可接受显式领域模型、事实与导入映射，但不执行 SWRL。增加清单或改文件名不等于完成加载适配。

## 2. 文件最低内容

| 文件 | 必须表达 |
|---|---|
| subontologies/<domain>_ontology.owl | 领域范围、稳定本体IRI/命名空间、模型版本、类/属性/关系、domain/range、身份、单位与来源；区分原始与派生事实 |
| rules/<domain>/<domain>_rules.swrl | 真实 `swrl:Imp`、body/head RDF列表和原子；规则ID、归属领域、依赖、条件、结果、例外、来源、适用范围、状态和必要人工标记 |
| formulas/<domain>.ttl（适用时） | 唯一可执行RDF表达树、原始LaTeX、参数/输出、单位、必要条件、依赖、来源与核验/激活范围；字段按所选公式后端合同解释 |
| integration/load-plan.ttl | 领域和模块登记、角色/路径/格式/版本/依赖、入口模式、ABox边界、离线解析与加载约定 |
| integration/merged_ontology.owl | 声明本体IRI、版本、源模块；明确物化结果或导入入口；与声明的构建源/闭包一致 |
| docs/<domain>_本体说明.md | 领域能力问题与边界、类与属性定义及来源、关系方向/特征、规则依据与案例关联、实例与数据映射、依赖、真实命令及未验证项；统计从实际图提取并说明去重/计数范围，结构见领域说明模板 |
| shapes.ttl | 类型、必填、枚举、范围、关系基数、目标类型、身份唯一性、关联键及时间/对象作用域 |
| provenance.ttl | 来源ID、标题、定位、版本/有效期、权威性、确认范围；能力问题与规则关联、假设、冲突与缺口；检索来源按需记录知识库/文档/片段、请求/快照和覆盖范围 |
| mapping.ttl | 源对象/字段、目标类/属性、业务键、转换、空值/单位/时间处理、关系创建方式及实现状态 |
| data/instances_<domain>.owl | 业务实例、事实、快照范围、synthetic/provided标记、字段与关系证据；不预写规则结论 |
| tests/cases.ttl | 案例ID、安全的输入相对路径、独立预期与依据；预期可以是分类、关系、决策状态/结果或明确拒绝 |
| README.md | 能力问题、已支持范围、后端及版本/profile、依赖、实际运行/测试命令、退出状态、Neo4j选择理由与缺口 |
| SKILL.md | 校验包、准备事实、调用后端、读取结果与证据、处理未知/冲突/人工项；不重新解释政策 |
| acceptance.md | 当次命令/版本/时间、检查结果、黄金与覆盖、反例、未执行项、日志位置及输入/模型/程序/输出指纹 |

设计阶段可使用 `design.md`补充能力问题、领域归属、对象决策表和未决项，并记录采用的主流程/专项方法、适用范围、阶段产物与必要调整依据；这些记录可并入已有项目文档，不另造平行流程。说明文档中的规则文字是阅读视图，实际条件仍由源OWL/SWRL唯一维护。自定义RDF词汇、加载和测试预期协议应在包内说明，不能只给不透明键值。

领域说明可从[领域说明模板](templates/domain-doc.md)生成，按文档要求完整覆盖本次范围内所有类、属性与规则的中文说明、用法及例证，不能只列重点实体。所有类、属性、公理与规则的设计判断须能追溯到材料或明确的建模选择；不把文档章节、检索分类或高相似度片段直接当作本体继承/等价关系。只核对过摘要时标明证据范围。

来源版本或生效期未提供时如实注明。每条规则的阈值、例外和优先级均须可定位到来源，不自行补审批或容差。`approved`只按实际确认范围解释，不代表鉴权、组织批准或某次业务动作的许可。

未确定的业务规则先记入设计与来源候选，不混入本次可执行规则图。`draft`、`inactive`等注释本身不会禁用 `swrl:Imp`；如需保存草案规则文件，须在独立草案位置并由实际加载机制显式排除，验收时证明未被执行。后端没有规则启停能力时，不能依赖状态标签，应保持候选为非执行记录或阻断受影响的运行。对合成草案规则进行结构/执行测试时明确测试范围，不据此激活真实业务政策。

## 3. 语义与数据约定

- 优先使用OWL、RDF/RDFS、XSD、SHACL、SWRL和Dublin Core等标准词汇。项目自定义词汇必须有固定命名空间与含义说明；已有项目保留稳定IRI。
- 对象先有身份和粒度，再有属性与规则。金额用 `xsd:decimal`及精确十进制计算；时间明确时区和有效范围。单位转换、聚合、舍入和尾差须有依据和实际实现。
- 每个业务字段和关系值均可追溯到来源和具体位置，可使用RDF reification、命名图等被所选工具支持的表示。报告中的证据必须指向实际存在的事实；来源引用不证明值真实或集合完整。
- 缺失、失败、无业务、空串、false和0分开。原始事实、派生事实、结论、人工确认和业务动作分开；映射说明与流程说明不代表转换、审批或调度已经执行。
- OWL描述语义，SHACL检查输入约束，SWRL承载规则。domain/range或FunctionalProperty不能替代输入完整性、复合唯一键和业务关联检查。
- 业务领域是范围与维护边界，不等同于属性的 `rdfs:domain`；无需为目录分组虚造业务类。TBox不夹带当前业务快照，ABox不夹带改写政策的公理或规则。确有固定枚举个体时说明归属与生命周期。
- 后端直接读取原生语义文件。若需要适配/编译，转换必须可追溯、可重建并验证等价，不能成为第二套手工维护的政策，也不能输出JSON。
- 可以用代码辅助首次生成原生模型、格式转换或集成构建，但交付后明确源文件与派生产物的维护关系。不能一边维护SWRL、一边在Python前向链或测试中重新手写同一批业务条件并据此宣称SWRL已运行；后端缺失时保留未执行范围。

## 4. 后端与智能体约定

README列明实际支持的OWL语义、SWRL原子/内建函数、变量绑定、数据类型、聚合/算术限制及校验顺序。不支持的表达明确拒绝或列缺口，不删除条件近似执行，不从文件能解析推定完整标准已支持。

使用[计算协同](Ontology-tools/CALCULATION.md)时，声明实际函数、数据类型、精度、舍入／时间业务依据及资源预算；计算代码仅实现通用函数，业务公式仍在原生规则中。保留适配前输入及 UTC 时间工作视图的转换映射；说明前置 SHACL 检查原始图、后端／规则／后置检查使用哪个视图。新值可以由成功规则头加入候选，不能将所有中间变量或未命中分支的值当作事实。

上述“公式仍在原生规则中”适用于旧 `hermit-swrl-calculation-v1`。采用[结构化公式合同](Ontology-tools/FORMULA.md)的 `hermit-swrl-formula-v1` 时，RDF表达树是公式唯一执行源，OWL/SWRL负责概念、诊断与适用性，SHACL维护完整性和参数关联；原始LaTeX用于展示，不由大模型临时解释求值。静态目录与动态评估记录分开，评估绑定同一对象/工况及有依据的必要条件；只有完整计算成功的结果可扩张后续数据候选，失败或未命中的中间值不能作为事实。算法精度、单位转换、舍入与资源预算按后端声明留证，不把数字精度当成物理容差。

决策型项目单独定义未知、冲突、无匹配和人工复核的归并规则及优先级，并说明依据；它们属于项目应用语义。不能把“未推得”当作否定，不能凭结果文案临时猜测人工标记。输出中显式保存人工状态，不表示已完成移交或审批。

大模型组织事实、调用实际后端、解释保存的结果与依据；仅阅读规则后的语言判断不得标为已执行推理。Neo4j按关系存储/查询需求选择，不替代SHACL，也不自动提供完整OWL/SWRL推理。

## 5. 结果、验收与冻结

推荐运行输出为 `input.ttl`、`result.ttl`、`shacl-report.ttl`、`execution.ttl`、`report.md`；黄金测试输出 `test-report.ttl`和 `test-report.md`。名称可随后端调整，README须列实际文件和读取方式，不生成JSON。

采用 `Ontology-tools` 包执行时另保存 `closure.ttl`、`trace.ttl`、按配置执行的后置 SHACL 报告及 `snapshot/package/`。OWL 投影另保存分类和候选范围，协同运行增加逐轮证据；独立 OWL 入口保存其原始输入和装配图。`result.ttl` 是新增推导图，`closure.ttl` 是明确范围内的查询视图。复跑核对输入/程序/依赖，比较语义状态和 RDF 图，不以序列化文本逐字相等代替图语义比较。已完成的 OWL 不符合结果可复核但不算本体验收通过，技术失败与未执行阶段如实记录。

证据强度与后端一致：受支持 SWRL 保存规则与直接前提，HermiT 导出保存对应结论、实际轮次及输入快照，不宣称逐公理证明或最小冲突解释。协同推导须保存冻结命名个体及实际数据候选范围；计算配置另保存初始与逐轮候选、新值来源、计算轨迹和合同、预算及时间规范化映射。类／属性／命名个体冻结，只有成功规则头的字面值可扩张候选；匿名存在对象不转换为无来源业务实体，固定点不等同完整 OWL DL＋SWRL 联合推理。

结果包含对象、查询/决策、状态、推导事实或结论、命中规则、公理/输入证据、来源和人工项。执行记录包含真实命令、退出码、UTC时间、后端/模型版本和SHA256。测试记录实际/预期、通过数量、规则或公理覆盖及未覆盖项，不能只有“全部通过”。

本体构建、集成或公理变更后须实际执行 OWL DL profile、全局一致性与具名类可满足性检查，固定 TBox/ABox 加载范围，SWRL 分开验证。保存真实推理器与版本、输入/程序/依赖指纹、全局结论及不可满足类；全局一致但存在具名不可满足类仍不通过，技术失败不能写成“本体不一致”。本地入口与命令见 [OWL-DL](Ontology-tools/OWL-DL.md)。

分别报告来源核对、模型解析、OWL语义检查、SHACL、实际推理、外部联调和业务批准。未执行写 `not_run`；SHACL通过不等于推理通过、事实真实或政策有效。未知或人工预期测试通过，不转为业务自动完成。

结构化公式另报告激活/待核验/不支持数量，激活公式必须逐一有独立算例并通过；数值、单位、输入关联、适用条件、依赖链及错误参数分别验证。公式覆盖与SWRL实际规则覆盖率至少80%的既有门槛分别统计，不能将公式条目数计作规则命中。完整中文问题经事实提取、追问、选公式、实际求值与证据解释的流程验证也应单列，不以手写RDF输入替代该层验收。

领域结构另验证模块完整性、依赖可解析性、规则符号及关系方向、源与集成结果的图等价和ABox加载范围。有跨域能力问题时使用独立跨域黄金案例与缺模块反例；没有跨域需求时不制造跨域用例。打开图形工具看到节点，只证明该视图加载了这些内容，不证明规则执行或集成一致性。
