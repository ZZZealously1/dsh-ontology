# 业务域、模块与集成入口

本方法用于新项目划分领域，或既有项目增加领域、拆分模块、融合外部模型时。目录和最低交付项以 [CONTRACT](../CONTRACT.md) 为准；记录设计可用[项目设计模板](../templates/project-design.md)，具体对齐与迁移步骤见[变更与复用](../skills/ontology-validation/references/change-and-reuse.md)。

## 1. 什么是本体域

业务域是围绕一组能力问题形成的语义与维护边界，例如物项替代。一个域可以涉及多张数据表、多个类和多个流程步骤；也可以与其他域共享物料、组织等术语。领域数量由问题与责任决定，不按类数、表数或文件数机械拆分。

- 领域 ID 是稳定的组织标识，用于模块、规则、说明和测试的关联，不要求建立 `Domain` 业务类。
- `rdfs:domain` 约束属性主体的语义类型，属于公理；它不是业务范围、文件归属或输入校验。
- `classes.owl` / `properties.owl` / `rules.swrl` 是按技术内容拆分。除非各自有独立业务范围和能力问题，否则不能称为三个业务域。
- TBox 定义概念、公理和属性；ABox 表达个体与事实。领域划分与 TBox / ABox 划分是不同维度。

每个域登记：稳定域 ID 与名称、范围及非目标、能力问题、权威术语与规则、维护责任、稳定本体 IRI、术语命名空间、版本、来源、共享术语及固定依赖。单域项目也登记这些内容，不需要制造多域结构。

## 2. 从业务域落到源文件

新包默认采用下列对应关系，根目录统一命名为 `ontology/`，以下路径均相对于该目录，不再嵌套另一层 `ontology/`：

| 职责 | 路径 | 维护方式 |
|---|---|---|
| 领域 TBox | `subontologies/<domain>_ontology.owl` | 同域类、属性与公理集中维护 |
| 领域规则 | `rules/<domain>/<domain>_rules.swrl` | 原生 SWRL；每条规则有域归属、稳定 ID 与来源 |
| 领域公式（可选） | `formulas/<domain>.ttl` | 原生RDF表达树及参数、单位、条件、来源；不混入动态事实 |
| 领域 ABox | `data/instances_<domain>.owl` | 事实快照，记录来源、时间、真实或合成标记 |
| 领域说明 | `docs/<domain>_本体说明.md` | 范围、概念、关系、规则定位、依赖与限制 |
| 集成入口 | `integration/merged_ontology.owl` | 默认由 TBox 与规则源构建，不手工维护政策副本 |
| 加载契约 | `integration/load-plan.ttl` | 域、文件角色、格式、版本、本地路径与依赖 |

`.owl` 与 `.swrl` 固定为 RDF/XML，`.ttl` 固定为 Turtle；扩展名不替代格式校验。无业务规则的域不制造空 SWRL，无实例输入的模型草案说明缺口。`shapes.ttl`、`provenance.ttl`、`mapping.ttl`、测试及运行记录保留各自职责，不塞入集成本体充当业务公理。

本体 IRI 标识逻辑模块，术语命名空间标识概念，版本 IRI（如采用）标识具体发布，包内路径标识本地文件；四者分别登记。模块可共享命名空间，但要能确定每个术语的权威定义处。既有项目保留稳定 IRI，不为适配目录而重命名业务身份。

## 3. 共享与跨域关系

共享术语只维护一份权威定义，其他域引用它的 IRI。复用确有必要时可建立共享模块；规模小、单域或只是目录整齐时不强制增加基础域。

为每条跨域关系或桥接规则记录定义方、两端类型与方向、身份和时间范围、所依赖版本、来源与独立案例。候选匹配先写入映射并核对定义和成员范围；同名、相似度和默认置信度不直接生成等价关系。已确认的类对齐使用适当的类关系，属性对齐使用属性关系，`owl:sameAs` 仅用于证据充分的个体同一性；详细判定见[融合与对齐](../skills/ontology-validation/references/change-and-reuse.md#融合与对齐)。

确需对齐时把有依据的桥接公理或规则作为明确归属的维护源，并登记依赖。归属于既有域即可时不新增模块；多方共同维护的桥接确有独立职责时，可作为共享/桥接模块列入加载清单，不虚构一个业务域。不能在合并脚本中偷偷改写含义，也不能只在文档里声明已对齐。

检查域间循环依赖是否来自共享术语归属不清。若必须共同发布，明确版本与验收边界；不要把文件可以分别解析当成模块可以独立使用。

## 4. 集成不等于语义融合

设计时声明本次操作及其产物，避免把同一种文件名用于不同承诺：

| 操作 | 语义变化与产物 | 验证依据 |
|---|---|---|
| 模块装配 | 源定义不改，生成物化并集或本地导入入口 | 声明源集合、空白节点安全、图同构或完整导入闭包 |
| 概念融合 | 有依据地复用、对齐或调整定义，再从源构建入口 | 对齐决策、冲突处理、明确的公理差异、实际语义检查及联合案例 |
| 部署或格式适配 | 为后端产生兼容布局或序列化，保持声明的源语义 | 格式/加载契约、源到产物映射、保真比较及后端回归 |

同一项目可能同时执行多种操作，应分别记录。融合先分析同名异义、异名同义、层次、属性和规则冲突，再依据来源决定处理；没有依据的冲突保留未决。来源导入顺序、命名空间不同或属性并集不能代替语义判断。

默认集成入口是领域 TBox 与所需 SWRL 规则的派生 RDF 图。构建器逐文件解析并保持空白节点作用域独立，然后合并；核对 IRI 重定义、规则引用、版本、RDF 列表和所有源文件覆盖。图并集不自动发现所有逻辑冲突，也不自动对齐同名概念，仍需所选后端的语义检查与跨域案例。

构建契约同时列明各源 `owl:Ontology` 头部、版本、imports 与新集成头的保留/转换方式及比较范围，不能构建后临时删除元数据使检查通过。现有结构模板保留源图并添加集成头，且拒绝imports；其他加载器对本体头的要求须在项目中验证。需要重组头部时保留原模块身份与版本追踪，并事先声明具体变换及等价检查范围。

动态 ABox 不默认烘焙进模型入口；运行时按加载契约选定领域事实与快照。需要可视化演示快照时单独声明其包含的数据与版本，并避免与运行事实重复加载。推导结果仍是运行输出，不反写为原始事实。

纯 `owl:imports` 入口也是可选模式，但必须明确标记；在声明的本体节点上记录被导入的本体/版本 IRI，通过本地 IRI 映射固定每个依赖的版本和文件，不用解析器临时图标识替代本体身份。实际加载器须离线解析完整闭包，包括所需规则；没有规则导入或显式加载时，不能宣称规则随入口一起载入。导入声明不是已经合并的完整图，也不授权联网下载。

集成和兼容导出只从源重建。保留真实命令、源到产物映射和指纹，验证应有的 RDF 图语义与来源覆盖；不能通过改扩展名转换格式，也不能手改派生模型修补业务规则。比较空白节点时使用图同构；类数、规则数或三元组数只是盘点信息，不是完整性或逻辑一致性的证明。有意融合造成的公理变动逐项记录，不能要求它与未修改的原始图相等后再隐去差异。

## 5. 清单与后端的接口

`integration/load-plan.ttl` 是项目加载契约。其词汇和解析语义须在包内说明：模块属于哪个域，角色是 TBox、规则、ABox 还是派生产物，文件如何解析，使用什么格式与版本，依赖谁，当前集成与运行到底选择哪些文件。仅写清单不会让任何引擎自动认识它；需要实际读取清单的加载器，或能够从清单产生确定调用参数的适配步骤。

采用[结构化公式配置](../Ontology-tools/FORMULA.md)时，加载清单另列 `FormulaCatalog` 角色和所需的 `formulas/<domain>.ttl`。目录是静态公式定义源，独立于TBox、SWRL和动态ABox；按请求选择公式及完整依赖，避免将完整目录当作OWL候选事实。扁平执行包增加 `formulas.ttl`，适配器分别证明模型、规则、公式和事实源到导出图等价；现有模板构建器若尚不识别该角色，应明确扩展后再采用，不能仅改清单宣称已支持。

[Ontology-tools](../Ontology-tools/README.md) 的 `local-rules-v1` 规则执行接口使用扁平 `ontology.ttl`、`rules.swrl`、`inputs/facts.ttl`（事实可通过参数指定），不读取领域清单，不支持 `owl:imports`。选择它时应交付可重建的扁平兼容导出，并按其 [PROFILE](../Ontology-tools/PROFILE.md) 验证表达；或者另选支持本项目模型的后端。兼容导出可放单独目录或包外确定位置，不能让运行器把整份多域源目录误当成已适配输入。运行器能力以实际实现为准，文件布局不赋予新的推理语义。独立 [OWL DL 检查器](../Ontology-tools/OWL-DL.md)可显式加载多个纯模型/事实文件和递归本地导入映射，检查它们的全局一致性与具名类可满足性；它不读取领域清单或执行 SWRL。

旧扁平包继续有效，不因本规范批量迁移真实项目。新包或主动迁移时分别核验：源文件格式、域与模块登记、离线加载闭包、源与集成图对应、ABox 分离、后端支持和独立黄金案例。

## 6. 复用与演进

领域布局组织“模型—规则—实例—说明—集成入口”的职责，具体业务条款、阈值和事实仍须来自项目材料。已有模型先识别实际序列化、导入闭包和加载角色；不因文件后缀、名称或历史报告而认定已加载全部规则或通过验证。

融合或迁移按[变更与复用](../skills/ontology-validation/references/change-and-reuse.md)完成差异分析、候选对齐、冲突处理、新版本构建和回归，本文件提供领域、依赖与加载要求。映射使用原生RDF；标签相同不自动等价，来源优先级须有依据，图保真与业务行为分别验证。
